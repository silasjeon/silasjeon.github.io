Rethinking Interfaces for Large Language Models

2025/07/22

ChatGPT’s popularity has shaped a widespread perception that a chatbot interface is the natural and perhaps only way to interact with Large Language Models (LLMs). With applications like Claude, Gemini, Perplexity, Cursor, and numerous coding assistants, this view seems reinforced. The reality is more nuanced: the chatbot format is merely one possible design choice among many.

LLMs are stateless text-processing machines. They take input text and output text that is most likely to follow the input. They don’t retain any memory of previous interactions. The apparent conversational memory you experience in applications like ChatGPT isn’t built into the model itself. Instead, your conversation history is combined with your latest input each time, forming a new single input fed to the LLM at the application code level. From the LLM’s point of view, all the conversation history and the new prompts are equally the same text.

ChatGPT’s UX doesn’t give you this mental model for LLMs. When editing a prompt mid-conversation, ChatGPT discards all subsequent exchanges and regenerates a response from the edited point onward. This design implicitly suggests that conversations cannot be edited mid-stream.

Given this understanding, we can imagine other types of interfaces to utilize LLMs besides chatbots.

I developed an idea to address a common challenge known as “Context Engineering” in working with LLMs. The context window—the whole text given to the LLM with prompts—is important for LLMs to work well. Poorly managed contexts can lead to incorrect or irrelevant outputs. For example, if you need multiple turns to get the final answer from the LLM by giving required information incrementally (answering and guiding the LLM), it can perform worse than when you give all the information at once and ask the question. This is because the LLM refers to the previous premature answers when it responds later. But it is natural for users to ask and counsel with LLMs incrementally, as in the multi-turn chatbot interface. It requires knowledge and effort for users to consciously edit and delete the previous prompts and select useful outputs from the LLM.

To explore an alternative, I built a prototype that avoids the linear conversation model and instead gives users explicit control over what context is included at each step. In this interface, there is no conversation history, but there are multiple texts shown as cards serving as context. When the user sends a prompt, the cards can be either included as context or not, based on the user’s selection. The user can add the LLM’s response as a new card or just discard it. Texts in the cards can be edited at any time.

I believe this kind of interface will fit better for products designed for research or creative tasks, where you’re discovering something and can validate and curate the information based on your knowledge or taste. It won’t fit products that aim to provide a conversation partner.

I’d be interested to hear your thoughts on exploring ideas.
